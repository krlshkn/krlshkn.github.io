# 2. Концепция функционирования (CONOPS) — ParkPoint

## Участники (заинтересствованные стороны и роли)

**Клиент (арендатор)** — физическое лицо, которое ищет, бронирует и оплачивает парковочные места на определённый период времени (разово или по подписке).

**Владелец парковочного места** — физическое лицо, владеющее парковочным местом в жилом комплексе, желающее сдавать его в аренду для получения дохода.

**Менеджер парковочной зоны** — представитель ТСЖ, управляющей компании или ЖК, отвечающий за парковочную зону в целом (добавление зоны в систему, управление её статусом, взаимодействие с администратором).

**Администратор системы** — сотрудник, обеспечивающий работу платформы: управление пользователями, парковочными зонами, жалобами, модерация заявок, просмотр аналитики.

**Платёжная система (внешний сервис)** — банк-эквайер или платёжный шлюз, обрабатывающий транзакции по банковским картам.

**Картографический сервис (внешний API)** — сервис (Яндекс.Карты, Google Maps, OpenStreetMap), предоставляющий картографическую основу, геокодирование и поиск по адресам.

---

## Системные элементы (типовая конфигурация)

**Фронтенд (веб-приложение)** — пользовательский интерфейс для всех ролей (клиент, владелец, менеджер зоны, администратор). Обеспечивает отображение карты, форм бронирования, чата, личного кабинета, админ-панели.

**Бэкенд (ядро системы / Spring Boot)** — центральный модуль, реализующий бизнес-логику: регистрация/авторизация, управление бронированиями и подписками, расчёт стоимости, чаты, жалобы, отзывы, проверка доступности слотов.

**База данных (PostgreSQL)** — реляционное хранилище всех данных: пользователи, парковочные зоны, парковочные места, бронирования, подписки, сообщения, жалобы, отзывы, заявки на создание зон.

**Модуль шифрования платёжных данных (AES)** — компонент, отвечающий за безопасное хранение банковских карт пользователей. Шифрование выполняется по алгоритму AES (Advanced Encryption Standard) с длиной ключа 256 бит.

**Маршрутизатор бронирований (модуль проверки доступности)** — компонент, который при создании бронирования или подписки проверяет:
- пересечение с существующими бронями (`booking`),
- пересечение с активными подписками (`subscription`),
- статус парковочного места (`is_available = ACTIVE`),
- статус парковочной зоны (`state = ACTIVE`).

**Репозиторий документов (фотографий / медиа-файлов)** — объектное хранилище для фотографий парковочных зон, карт парковок, аватарок пользователей.

**Сервис уведомлений (email / push)** — отправляет уведомления об изменении статуса бронирования, получении новой жалобы, подтверждении/отклонении заявки на зону, сообщениях в чате.

**Журнал аудита (логирование действий)** — фиксирует в базе данных ключевые события: создание/изменение/удаление пользователей, зон, мест; изменение статусов бронирований; подтверждение/отклонение заявок; вход/выход из системы.

**Модуль очереди сообщений** — обеспечивает отказоустойчивость при недоступности картографического API, сервиса уведомлений или платёжного шлюза.

## Сценарий 1. Поиск и разовое бронирование парковочного места (Клиент → Владелец)

### Цель

Клиент находит свободное парковочное место через карту или поиск по адресу, создаёт разовое бронирование, оплачивает его онлайн и получает подтверждение от владельца.

### Условия начала

1. Клиент авторизован в системе (получил токен через логин/пароль).
2. В системе существует хотя бы одна активная парковочная зона (`state = ACTIVE`) с активными местами (`is_available = ACTIVE`).
3. У клиента привязана банковская карта (зашифрована в модуле шифрования) или добавлена в процессе оплаты.
4. Картографический сервис доступен (иначе отображение карты работает в режиме деградации — список зон).

### Основной поток (Happy path)

1. Клиент открывает главную страницу с картой — фронтенд загружает парковочные зоны из бэкенда и отображает их на карте через API картографического сервиса.
2. Клиент выбирает зону на карте или ищет по адресу (геокодирование через картографический API).
3. Фронтенд отправляет запрос на бэкенд: `GET /parking-zones/{id}/spaces-with-slots`.
4. Бэкенд обращается к Маршрутизатору бронирований, который запрашивает из БД:
   - список парковочных мест в зоне,
   - занятые слоты (бронирования со статусом `CONFIRMED` и будущие подписки на это место).
5. Бэкенд возвращает клиенту список мест со свободными временными интервалами.
6. Клиент выбирает место, дату и время начала/окончания.
7. Клиент нажимает «Забронировать». Фронтенд отправляет `POST /booking/create` с данными бронирования.
8. Бэкенд через Маршрутизатор бронирований выполняет **финальную проверку доступности** (на случай, если слот занят за секунды до подтверждения).
9. Проверка пройдена — бэкенд создаёт запись в таблице `booking` со статусом `PENDING`, вычисляет стоимость (на основе тарифов владельца).
10. Бэкенд через Модуль шифрования платёжных данных достаёт зашифрованную карту клиента, взаимодействует с платёжной системой для списания средств.
11. Платёж успешен — бэкенд обновляет статус бронирования на `CONFIRMED`.
12. Сервис уведомлений отправляет владельцу уведомление: «Поступила новая бронь на [дата/время]». Клиенту: «Бронь подтверждена, ожидайте уведомления от владельца».
13. Владелец заходит в личный кабинет, видит новую бронь со статусом `CONFIRMED`.

### Результат

Бронирование создано, средства списаны, статус `CONFIRMED`, клиент и владелец уведомлены. В журнале аудита зафиксировано событие: `BOOKING_CREATED`, `PAYMENT_SUCCESS`, `BOOKING_CONFIRMED`.

### Исключения (нештатные ситуации)

**1. Выбранный слот уже занят (конфликт при финальной проверке)**
- 1.1. Маршрутизатор бронирований обнаруживает, что слот уже занят другим подтверждённым бронированием или подпиской.
- 1.2. Бэкенд возвращает ошибку: «К сожалению, это место только что забронировали. Пожалуйста, выберите другое время или место».
- 1.3. Клиент возвращается к выбору слота. Деньги не списываются.

**2. Ошибка оплаты (недостаточно средств, карта заблокирована, платёжный шлюз вернул отказ)**
- 2.1. Платёжная система возвращает код ошибки.
- 2.2. Бэкенд **не создаёт бронирование** (или создаёт со статусом `PAYMENT_FAILED`, но немедленно отменяет).
- 2.3. Клиенту показывается сообщение: «Оплата не прошла. Проверьте карту или выберите другой способ оплаты».
- 2.4. Журнал аудита фиксирует `PAYMENT_FAILED` с кодом ошибки.

**3. Парковочное место временно недоступно (владелец сменил статус на `INACTIVE`)**
- 3.1. Маршрутизатор бронирований при проверке видит `is_available = INACTIVE`.
- 3.2. Бронирование блокируется, клиент получает сообщение: «Это место временно не принимает бронирования».

**4. Парковочная зона заблокирована администратором (`state = BLOCKED` или `INACTIVE`)**
- 4.1. При попытке бронирования в зоне маршрутизатор проверяет статус зоны.
- 4.2. Бронирование блокируется, клиент видит: «Парковочная зона временно недоступна».

### Режимы деградации (как продолжаем работать)

**Картографический сервис недоступен (таймаут, ошибка API)**
- 1.1. Фронтенд переключается в режим «Текстовый поиск и список зон» (без карты).
- 1.2. Клиент может выбрать зону из списка, посмотреть её адрес и перейти к бронированию.
- 1.3. При восстановлении картографического API карта отображается снова.
- 1.4. Журнал аудита фиксирует переход в режим деградации.

**Платёжный шлюз недоступен (эквайринг не отвечает)**
- 2.1. При создании бронирования бэкенд получает ошибку подключения к платёжному шлюзу.
- 2.2. Система переводит бронирование в статус `AWAITING_PAYMENT` (ожидает оплаты), но не блокирует слот.
- 2.3. Клиенту отображается: «Платёжный сервис временно недоступен. Попробуйте позже».
- 2.4. При восстановлении — повторная попытка оплаты.

**Сервис уведомлений недоступен**
- 3.1. Бронирование создаётся и оплачивается в штатном режиме.
- 3.2. Бэкенд ставит уведомления в очередь.
- 3.3. При восстановлении сервиса — массовая отправка накопившихся уведомлений.

**База данных недоступна при попытке бронирования**
- 4.1. Бэкенд не может проверить доступность слота и создать запись.
- 4.2. Возвращает клиенту ошибку 503: «Сервис временно недоступен. Попробуйте позже».

## Сценарий 2. Оформление подписки на парковочное место (Клиент)

### Цель

Клиент оформляет долгосрочную подписку на парковочное место на определённые дни недели и время (например, каждый рабочий день с 9:00 до 18:00) с ежемесячной оплатой.

### Условия начала

1. Клиент авторизован.
2. Выбрана активная парковочная зона и активное парковочное место.
3. У клиента привязана банковская карта.

### Основной поток (Happy path)

1. Клиент на странице бронирования выбирает **«Оформить подписку»** вместо разового бронирования.
2. Выбирает дни недели и временной интервал.
3. Фронтенд отправляет `POST /subscription/check` с параметрами подписки.
4. Бэкенд через Маршрутизатор бронирований проверяет:
   - пересечение с существующими бронями,
   - пересечение с другими подписками.
5. Проверка пройдена — бэкенд возвращает `true`.
6. Клиент подтверждает создание подписки. Фронтенд отправляет `POST /subscription/create`.
7. Бэкенд рассчитывает стоимость подписки, создаёт запись в `subscription`, затем через платёжный шлюз списывает средства.
8. Успех — подписка активируется. Владелец места получает уведомление.
9. Клиент видит подписку в разделе «Мои подписки».

### Результат

Подписка активна, средства списаны, на указанные дни/время место зарезервировано за клиентом.

### Исключения (нештатные ситуации)

**Конфликт подписки с существующими бронями**
- 1.1. Маршрутизатор обнаруживает, что в указанные дни/время место уже забронировано.
- 1.2. Проверка возвращает `false` с перечнем конфликтующих слотов.
- 1.3. Клиент видит сообщение: «В выбранное время место уже занято. Пожалуйста, скорректируйте расписание».

**Ошибка оплаты подписки**
- 2.1. Платёжный шлюз возвращает ошибку.
- 2.2. Подписка не создаётся, клиент получает уведомление.
- 2.3. Журнал аудита фиксирует `SUBSCRIPTION_PAYMENT_FAILED`.

### Режимы деградации

(аналогичны сценарию 1)

## Сценарий 3. Управление парковочным местом (Владелец)

### Цель

Владелец парковочного места может добавлять новые места, редактировать тарифы, временно отключать место.

### Условия начала

1. Владелец авторизован.

### Основной поток (Happy path)

**Добавление нового места:**
1. Владелец заходит в личный кабинет → «Мои места» → «Добавить место».
2. Заполняет форму: выбирает парковочную зону, указывает тарифы, описание.
3. Фронтенд отправляет `POST /parking-spaces/create`.
4. Бэкенд создаёт запись в таблице `parking_space`, статус `is_available = ACTIVE`.

**Редактирование тарифов:**
5. Владелец выбирает место из списка → меняет значения цены.
6. Отправляет `PUT /parking-spaces/update`.
7. Бэкенд обновляет запись в БД.

**Временное отключение места:**
8. Владелец переключает тумблер «Доступно для аренды» в положение OFF.
9. Бэкенд обновляет `is_available` с `ACTIVE` на `INACTIVE`.
10. Существующие будущие бронирования (`CONFIRMED`) остаются действительными.

### Результат

Парковочное место добавлено/отредактировано/отключено.

### Исключения

**Попытка удалить место с активными будущими бронями:**
- 1.1. Бэкенд проверяет наличие будущих бронирований со статусом `CONFIRMED`.
- 1.2. Если есть — блокирует удаление, возвращает ошибку.

**Некорректные тарифы:**
- 2.1. Валидация на фронтенде и бэкенде.
- 2.2. При нарушении — сохранение не происходит.

**Попытка владельца редактировать чужое место:**
- 3.1. Бэкенд проверяет `owner.id` из токена аутентификации.
- 3.2. Если не совпадает — возвращает `403 Forbidden`.

## Сценарий 4. Модерация заявки на парковочную зону (Администратор)

### Цель

Администратор обрабатывает заявку от менеджера зоны на добавление новой парковочной зоны в систему.

### Условия начала

1. Администратор авторизован с ролью `ADMIN`.
2. В системе есть хотя бы одна заявка со статусом `UNVIEWED`.

### Основной поток (Happy path)

1. Менеджер зоны отправляет заявку — `POST /application/create`. Статус `UNVIEWED`.
2. Администратор заходит в админ-панель → «Заявки на зоны».
3. Выбирает заявку, изучает данные.
4. Нажимает «Создать зону». Фронтенд отправляет запрос на создание.
5. Бэкенд автоматически заполняет поля новой зоны из заявки.
6. Администратор корректирует координаты, добавляет фотографии, указывает email менеджера.
7. Нажимает «Сохранить». Бэкенд:
   - создаёт пользователя с ролью `ZONE_MANAGER` (если такого email нет),
   - создаёт запись в `parking_zone` со статусом `ACTIVE`,
   - обновляет статус заявки на `ACCEPTED`,
   - отправляет уведомление менеджеру зоны.

### Результат

Парковочная зона добавлена, заявка закрыта.

### Исключения

**Администратор отклоняет заявку:**
- 1.1. Администратор нажимает «Отклонить», вводит комментарий.
- 1.2. Статус заявки → `REJECTED`, уведомление заявителю.

**Заявка обрабатывается повторно:**
- 2.1. Бэкенд проверяет статус перед созданием зоны.
- 2.2. Если статус не `UNVIEWED` — возвращает ошибку.

### Режимы деградации

**Объектное хранилище недоступно:**
- 1.1. Зона создаётся без фотографий.
- 1.2. При восстановлении — фото добавляются через редактирование.

## Сценарий 5. Подача и рассмотрение жалобы (Клиент/Владелец → Администратор)

### Цель

Пользователь подаёт жалобу на другого пользователя; администратор рассматривает и принимает меры.

### Условия начала

1. Пользователь авторизован.
2. Администратор имеет роль `ADMIN`.

### Основной поток (Happy path)

1. Пользователь открывает страницу чата или бронирования.
2. Нажимает «Пожаловаться», заполняет форму, отправляет `POST /complaint/create`.
3. Бэкенд создаёт запись в `complaint` со статусом `PENDING`.
4. Администратор в админ-панели видит жалобу, изучает контекст.
5. Принимает решение:
   - обоснована → статус `RESOLVED`, блокировка пользователя при необходимости;
   - ложная → статус `REJECTED`.
6. Бэкенд уведомляет участников.

### Результат

Жалоба рассмотрена, статус изменён.

### Исключения

**Жалоба на уже заблокированного пользователя:**
- 1.1. Система принимает жалобу, администратор видит пометку.

### Режимы деградации

(аналогично сценарию 1)

## Сценарий 6. Просмотр аналитики (Администратор)

### Цель

Администратор получает возможность мониторить активность системы.

### Условия начала

1. Администратор авторизован с ролью `ADMIN`.

### Основной поток

1. Администратор заходит в админ-панель → «Дашборд».
2. Фронтенд отправляет запросы:
   - `GET /stats/bookings` — бронирования за 14 дней,
   - `GET /stats/users` — распределение пользователей по ролям.
3. Бэкенд агрегирует данные из БД.
4. Фронтенд отображает графики.

### Результат

Администратор видит актуальную аналитику.

### Исключения

**Долгое выполнение статистических запросов:**
- 1.1. Использование материализованных представлений или кэширование на 1 час.
